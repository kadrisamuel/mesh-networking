# Verification and acceptance matrix v1.0.0-draft.2

- Status: Draft — human approval required; hardware, RF, legal, signing, and security-review rows are blocked pending named evidence
- Decision set: DEC-001, 2026-08-18
- Matrix version: `mesh-messenger-tests/1`

Every row defines an exact start event, end event, sample, timeout, environment, and pass rule. A row may report only `PASS`, `FAIL`, or `BLOCKED` with evidence. Mocks cannot pass a row marked physical, legal, signing, or human review.

## 1. Measurement rules

- All automated tests record source revision, clean/dirty state, tool/dependency versions, target, seed, start/end monotonic timestamps, ordered observations, failures, and SHA-256 evidence digest in canonical JSON.
- Unit/simulation tests use injected clocks, RNG, storage, and transports; they contain no real sleeps. Physical performance tests use a monotonic platform clock.
- Unless a row states otherwise, per-message time starts immediately after the sender's private transaction enters `queued` and ends immediately after the recipient's private transaction commits the authenticated plaintext/event.
- For 100 timed samples, p95 is nearest-rank observation 95 after ascending sort. Warm-up samples are excluded and identified. A timeout is retained as its timeout value and a failure; it is not discarded.
- “No internet” means cellular disabled, test WLAN WAN physically disconnected, DNS default route absent, and a simultaneous packet capture showing no packet to a non-link-local address.
- Packet/text scans use unique 32-byte canaries for message, display name, root/device keys, SQLCipher key, MLS group ID, routing secret, recovery phrase prefix, contact QR, and peer address. A test passes only when expected private-memory/private-database controls find every canary and prohibited artifacts find none.
- A physical row starts only after HW-001 records actual model/serial, OS/firmware, antenna, battery health, cables, and calibration. RF rows additionally require the signed jurisdiction/venue/power/duty-cycle checklist.

### 5.1 Exact `MLS-ROLLOVER-001` crash schedule

Run the following 18 cases for each of the two direct-chat sender contexts and all 16 private-group sender contexts, resetting durable state before every case:

1. At `seal_count = MAX_SEALS - 2`, run three ordinary-seal cases: uninterrupted; crash after all transaction writes but before commit; and crash immediately after commit before emission. The first and third recover count `MAX_SEALS - 1` with one byte-identical stored ordinary envelope; the pre-commit crash recovers count `MAX_SEALS - 2` with no reservation or envelope.
2. At `seal_count = MAX_SEALS - 1`, run one uninterrupted rollover plus crash injection at exactly these ten cuts: before transaction begin; after staged ID/nonce reservation; after staged old counter becomes `MAX_SEALS`; after pending self-Update creation/old-epoch serialization; after immutable outer envelope staging; after merged new MLS state staging; after new exporters/zero counter staging; after outbound retry-record staging immediately before commit; immediately after commit before the relay call; and after first relay enqueue before custody status. Every pre-commit cut recovers `ROLLOVER_REQUIRED` with no consumption. Every post-commit cut and the uninterrupted case recover the exact same stored Update bytes, old count `MAX_SEALS`, merged new state/exporters, and new count zero. Retransmit the stored Update twice, require byte equality, deliver it after one already stored new-epoch application envelope, require the recipient to authenticate the Update with the old context, rescan without relay mutation, and accept that first new-key application exactly once.
3. At old `seal_count = MAX_SEALS`, run three creation attempts: ordinary envelope, new self-Update, and re-encryption of the stored Update. All three fail before RNG/MLS mutation; transmission of the existing stored envelope remains allowed and byte-identical.
4. At `seal_count = MAX_SEALS - 1`, deliver one valid incoming epoch transition before local rollover begins. It applies atomically, leaves the unused old count unchanged, initializes the new count to zero, clears `ROLLOVER_REQUIRED`, and permits one successful new-key ordinary send.

This is `(3 + 11 + 3 + 1) × 18 = 324` finite cases. No real sleep, probabilistic crash point, or additional generated case is part of this row.

### 5.2 Exact `PRO-FRAG-001` schedule

For fragment counts `n = 2, 4, 7, 10`, execute these finite schedules in this order:

1. All `2^n` loss masks, with surviving fragments delivered once in ascending index order and the monotonic clock advanced to exactly 600 seconds after the first fragment. This contributes `4 + 16 + 128 + 1,024 = 1,172` schedules.
2. For each counter `j = 0..255`, create one complete order/duplicate schedule. For every fragment index `i`, create `1 + (SHA-256(UTF8("PRO-FRAG-001/duplicates") || I2OSP(n,1) || I2OSP(j,2) || I2OSP(i,1))[0] mod 3)` occurrences. Sort all occurrences by `SHA-256(UTF8("PRO-FRAG-001/order") || I2OSP(n,1) || I2OSP(j,2) || I2OSP(i,1) || I2OSP(copy_index,1))`, breaking a digest tie by `(i, copy_index)`, and deliver in that order. This contributes `4 × 256 = 1,024` schedules.
3. For each size, one two-gateway complete schedule alternates gateway A/B frames and uses `a5`/`5a` only in the ignored final tail: 4 schedules.
4. For each of the 23 fragment positions across the four mappings, one schedule sends the cached frame three times and checks byte identity: 23 schedules.
5. For each of those 23 positions, run exactly three rejecting schedules: wrong envelope ID, wrong fragment count, and a one-bit flip in the first meaningful data byte: 69 schedules.
6. One cache-pressure schedule opens 129 ten-fragment assemblies in ascending envelope-ID order, then advances 600 seconds: 1 schedule.

The total is exactly `1,172 + 1,024 + 4 + 23 + 69 + 1 = 2,293`. No unbounded duplicate count, permutation set, property generator, or real sleep is part of this row.

## 10. Required evidence bundle

Each execution stores, under a later task-owned evidence path, the canonical result JSON, raw measurement data, environment manifest, seed/loss schedule, capture or trace digest, command line, and artifact hashes. Hardware and human evidence additionally contains reviewer/operator name, date, scope, source revision, actual device IDs, and signed outcome. Sensitive captures remain access-controlled and are represented in the bundle by digest plus retention location, never copied into public artifacts.
